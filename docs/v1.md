# Version 1

Version 1 of `plans` defines the stable core of the planning control plane.

The goal is deliberately narrow: provide a portable and deterministic way to take implementation
work from an initial plan to a recorded result, without coupling the plan format to
a particular coding agent, model provider, machine, or repository checkout layout.

## Core workflow

The v1 workflow is:

``` text
draft
  │
  │ plan ready
  ▼
next
  │
  │ Git checkpoint + execution
  ▼
open
  │
  │ implementation
  ▼
results
  │
  │ plan complete
  ▼
done
```

A plan may also leave the active lifecycle through `discarded`.

Before execution begins, the implementation-ready version of a plan must be preserved as a Git checkpoint.
Execution tooling must reject a selected `next` plan that is not present in `HEAD` or has uncommitted
changes. This invariant is enforced by the execution layer rather than `plans` itself.

## Stable core

Version 1 is expected to provide stable semantics for:

- plan metadata and structure;
- lifecycle states and transitions;
- readiness validation;
- completion validation;
- machine-readable inspection through `plan inspect --json`;
- logical repository references independent of local checkout paths.

Lifecycle transitions that affect the meaning of a plan should be protected by deterministic validation.

In particular:

- `next` means the plan is ready to implement without unresolved design work;
- `open` means implementation has started;
- `done` means the declared completion criteria and result requirements have been satisfied.

## Boundaries

`plans` owns planning state and lifecycle semantics.

It does not own:

- repository checkout management;
- coding-agent invocation;
- provider or model selection;
- agent session management;
- retries or queues;
- pull request creation;
- CI execution;
- multi-agent orchestration.

Those capabilities belong to execution and coordination layers that consume the `plans` interface.

This boundary allows the same plan to be executed by different tools without changing its representation.

## Version 1 readiness

Before `v1.0.0`, the core workflow should be exercised on real implementation work and
the following public contracts should be reviewed for stability:

- CLI command names and semantics;
- lifecycle states and allowed transitions;
- plan metadata;
- readiness semantics;
- completion semantics;
- `plan inspect --json`.

The implementation-ready plan used for execution and the completed result should both be recoverable from Git history.

Once these contracts have proven sufficient for normal use without requiring fundamental changes
to the plan schema or lifecycle, the core can be considered ready for `v1.0.0`.

Features outside these boundaries can continue to evolve independently after v1.
